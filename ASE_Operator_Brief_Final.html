1.3 Problem 1: Prompt Token Accumulation Drives Cost

Average prompt tokens per request grew from 871 to 1,981 over 14 days (+127%) — a near-perfect linear increase of 85.89 tokens/day (R² = 0.9997).

DayAvg Prompt TokensAvg Cost/Request
Jun 1871$11.0
Jun 71,379$17.1
Jun 141,981$24.3

Why we know this is a system prompt issue (not user behavior, not retrieval, not route mix):

  • Growth is identical across all three routes: policy_only +85/day, inventory +86/day, mixed +88/day. Since policy_only doesn’t call inventory at all, the growth must be in shared prompt infrastructure.
  • Retrieval payload is flat at ~1,155 bytes/day with zero trend (R² = 0.02).
  • Zero correlation between retrieval payload size and prompt tokens (r = -0.02).
  • Every user is unique — 1,200 requests from 1,200 distinct user hashes, each appearing exactly once. This rules out conversation history accumulation.
  • Growth is uniform within each day — coefficient of variation is ~5%. Not driven by outliers.
  • Route mix proportions don’t trend. Can’t explain growth via shift toward higher-token routes.

100% of cost growth traces to input token inflation. The cost formula: prompt_tokens × $0.012 + completion_tokens × $0.0024 (verified with zero prediction error). Under this formula, $1,121 of $1,122 total cost increase comes from input tokens.

Prompt token variance is high (stdev 354, range 669–2,100). This variance prevents OpenAI’s automatic prompt caching from activating consistently. A chunk budget would reduce this variance alongside fixing the growth.

Most likely causes: An automated process (cron job, daily deployment, content sync) appending few-shot examples, knowledge base metadata, or behavioral instructions to the system prompt.

Inventory retries almost always succeed (95.6%) — transient latency spikes, not persistent failure. OpenAI retries fail 26% — mainly sustained 429 rate limiting. Inventory retry rate jumped 3.5% → 12.1% in Week 2.

2. What I Would Do Next

2.1 Phase 1 — Stabilize Weeks 1–2

Action 1: Diagnose and Halt Prompt Token Growth Top Priority

Work directly with your engineering team to review the system prompt template and any automated injection pipelines. Identify what adds ~86 tokens/day, cap it, target stable prompt under 1,000 tokens.

Look for: daily cron jobs appending few-shot examples, logging that injects prior context, growing tool/function schemas, expanding metadata injected outside retrieval span.

Action 2: Investigate Inventory Service + Implement Graceful Degradation

Your infrastructure team determines what changed June 8–9. In parallel, implement graceful degradation with explicit partial answers:

  • When inventory fails but retrieval + OpenAI succeed: serve the policy-based answer with a caveat: “I don’t have live inventory data right now, but here’s the policy information.”
  • When OpenAI fails: return a static fallback directing employees to alternative resources.
  • Never return a raw 500/502/504 error to the employee.

Add a circuit breaker: after N consecutive inventory failures, skip the call and fall through to partial-answer handler immediately.

Action 3: Implement User Feedback Mechanism

Thumbs-up/down after every response in OneStore widget, linked to trace_id. Log to durable store (DynamoDB or equivalent). Minimum viable signal for answer quality and prerequisite for diagnosing the 1.0 queries/user problem.

Action 4: Enable Prompt/Completion Logging

Log full prompt + completion for 10% of requests to restricted S3 bucket, linked to trace_id. Privacy-review with security/compliance. Required for retrieval quality audit, eval pipeline, and debugging prompt growth.

Action 5: Quick Configuration Fixes

Three one-line fixes:

  • Raise max_tokens to 1,024: Eliminates 5.2% truncated responses. Cost impact: negligible.
  • Remove tool/function definitions from policy_only: Saves ~73 tokens/request on 49% of traffic.
  • Review OpenAI usage tier: If Tier 1, the 6 throttle events may resolve by reaching Tier 2.
Action 6: Set Up Monitoring and Alerting

Alerts for: inventory p95 > 500ms, error rate > 3%/hour, daily prompt token average exceeding threshold, any OpenAI 429 events. The Week 2 degradation should have been caught within hours.

2.2 Phase 2 — Optimize Weeks 3–6

Action 7: Parallelize Retrieval and Inventory Calls

Replace serial await with Promise.all([retrieval(), inventoryLookup()]). Saves 70–140ms on 51% of traffic. Low effort, high impact, zero risk — no dependency between these calls.

Action 8: Implement Retrieval Chunk Budget

Cap retrieved context at fixed budget (e.g., top 3 chunks or ~800 tokens). Makes prompt size predictable, enables prompt caching, reduces baseline size. Tune after retrieval quality audit.

Action 9: Enable OpenAI Prompt Caching

Automatic for GPT-4o/GPT-4o-mini since Oct 2024. Caches prefix ≥1,024 tokens. 50% discount on cached tokens, up to 80% faster TTFT.

Key requirement: Static content (system prompt, tool defs) must come at the beginning. Variable content (retrieval, user query) at the end. Prefix matching is exact.

Current: 0% cache hits. With prompt at ~1,700+ tokens, caching should be automatic — but only with proper prefix structure. Also consider prompt_cache_key and extended cache retention for high-traffic use.

Action 10: Evaluate Model Routing (GPT-4o vs GPT-4o-mini)
ModelInput PriceOutput Price
GPT-4o$2.50/M tokens$10.00/M tokens
GPT-4o-mini$0.15/M tokens$0.60/M tokens

GPT-4o-mini is ~94% cheaper. For 49% policy-only traffic, massive cost lever. But quality must be validated first with eval suite (200 representative questions, side-by-side scoring).

Action 11: Consider Fine-Tuning to Compress Prompt

If prompt growth is from behavioral instructions, fine-tuning GPT-4o encodes behavior into weights — potentially eliminating 1,500+ tokens. Training: $25/M tokens. Minimum: 50–100 examples. Prompt caching still works on fine-tuned models.

Action 12: Optimize Function Calling

Remove tool defs from policy_only. Use Structured Outputs (strict: true) for inventory responses — 100% schema adherence. Describe when (not) to use each function in system prompt.

Action 13: Add Shared Caching Infrastructure

Redis/ElastiCache for component-level caching:

  • Retrieval cache: Key on embedding similarity ≥0.95. TTL: 6–24hr. Expected: 20–40% hit rate.
  • Inventory cache: Key on product_id + store_id. TTL: 10min. Expected: 30–50% hit rate.
Action 14: Implement Proper Retry Strategy

Classify errors: 429 → retryable (respect Retry-After). 500/502/503 → exponential backoff (200ms→400ms→800ms + jitter). 400/401/403 → not retryable (fail fast to graceful degradation).

Add circuit breaker per downstream service: after N failures in rolling window, skip call entirely.

2.3 Phase 3 — Expand Weeks 7–12

Action 15: Build Evaluation Framework

Golden dataset of 200+ representative questions with expert-validated answers. Metrics: accuracy, completeness, faithfulness, format. Model-graded evals (GPT-4o as judge). Run before every change. Makes quality visible and measurable.

Action 16: Implement Streaming End-to-End

Current TTFT: ~1,000ms. With streaming: ~150ms. Three layers: OpenAI (stream: true), Lambda Function URL (response streaming), OneStore widget (SSE consumer). The single biggest UX improvement available.

Action 17: Request AWS Lambda Concurrency Increase

Current peak: ~420. At 4×: ~1,680 (above 1,000 default limit). Request increase to 2,500+. Configure provisioned concurrency of 350–400 for peak hours via CloudWatch Events.

Action 18: Verify OpenAI Usage Tier

Check Settings → Limits. The 6 throttle events suggest burst spikes exceeding per-second sub-windows. If Tier 1, reaching Tier 2 (auto with $50+ spend) may resolve. Can facilitate internal escalation.

Action 19: Implement Per-Team Cost Attribution

Separate API keys or project tags per team. Per-team usage limits to prevent runaway costs from any single team’s experimentation.

Action 20: Load Test the Complete Pipeline

At projected 4× volume during simulated peak. Validate all components handle increased concurrency. Onboard one team as pilot, monitor one week, then expand to remaining two.

2.4 Features Evaluated But Not Recommended

OpenAI Batch API: 50% cost discount but 24-hour turnaround. Not viable for a real-time assistant. Useful only for offline eval runs or FAQ pre-computation.

Assistants API: Built-in conversation threading, but the assistant’s single-turn nature (1.0 queries/user) doesn’t benefit. Migration complexity without clear benefit.

4. How I Would Advise on Tradeoffs

Decision 1: Model Routing (Cost vs. Quality)

Option A: Switch policy_only (49%) to GPT-4o-mini. ~94% cost reduction. Scores 82% on MMLU. Gate: eval suite, proceed only if quality drop <5%.
Option B: Keep GPT-4o everywhere, focus only on prompt compression. Zero quality risk but smaller savings (~30–50%).
Recommendation: Pursue Option A — biggest single cost lever. But never ship without eval validation.

Decision 2: Prompt Compression vs. Fine-Tuning (Cost vs. Effort)

Option A: Manual trim — identify and remove growing content. Fast (days), low risk.
Option B: Fine-tune GPT-4o to encode behavioral instructions. Eliminates bloat permanently but higher effort (weeks).
Recommendation: Fix immediate growth first (A), then evaluate fine-tuning (B). Sequential, not exclusive.

Decision 3: Expand Now vs. Stabilize First (Speed vs. Risk)

Option A: Expand immediately. 3 teams get access sooner. But inherit 8.2% peak failure rate and escalating costs.
Option B: Stabilize 4–6 weeks, then pilot. New teams launch on solid ground.
Recommendation: Stabilize first. An unreliable tool that employees abandon is worse than a delayed one they trust. Retail word-of-mouth is powerful.

Decision 4: Streaming (Latency Perception vs. Engineering Effort)

Option A: Implement streaming end-to-end. TTFT: ~1,000ms → ~150ms. Changes at three layers. Medium effort.
Option B: Keep synchronous. Less work but employees still stare at blank screen 1+ second.
Recommendation: Implement in Phase 3 after stabilization. Single biggest UX improvement. Directly addresses the 1.0 queries/user concern.
On Quality: We cannot measure answer quality from telemetry alone. finish_reason tells us about completion, not correctness. Build an evaluation suite: 200+ questions with known-good answers, scored by domain experts or LLM-as-judge, run before every change. This makes quality visible and measurable rather than anecdotal.
